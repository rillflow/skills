# cross-check — 2つのモデルの独立判断を主張台帳に残す

## 目的

ClaudeとCodexが同じ問いを独立に判断し、食い違った主張だけを相手の原文と根拠で交換する。どの主張が新しい根拠で変わり、どの不一致が判断として残ったかを主張台帳に残す。合意そのものは成果物ではない。

## 使う場面

| 場面 | ideation | cross-check |
|---|---|---|
| 複数の案・別の進め方・長所短所を求められた。答えが決まっていない設計・方針 | 使う | その判断が構造・共通ルール・費用・評価基準・後続作業を左右するなら使う。文書の中の判断も、内容が設計・方針・評価・選択の妥当性なら同じ。文書の種類だけでは使わない |
| 別のAIの意見を持ち込んで「どう思うか」と聞かれた | 必要なら使う | 使う。持ち込まれた側の検討は再利用し、手順1を省く |
| 共有・返信の文面 | 迅速モード | 表現を整えるだけなら使わない。文面が設計・方針・選択の妥当性を判断するなら1行目に従う |
| 調査・照会、決まった修正、通常のコードレビュー、表現の選択 | 使わない | 使わない |

- 利用者が明示的に依頼したら、上の表で使わない場面でも使う。
- このスキルを使っても、ファイルの変更や公開の権限は増えない。
- ideationが入っていない環境では、各モデルが問題の枠と候補を自分で書き出してから結論を出す。

## 役割

| 役割 | 担当 | すること |
|---|---|---|
| 呼び出し元 | いま利用者と話しているセッションのモデル | 問い・資料の版・上限を決め、主張台帳を書き、ラウンドを数え、終了と推奨を判断する。自分の側の独立判断も書く |
| 実行役 | 呼び出し元が起動するサブエージェントや下位モデル | 相手のCLIの呼び出し、応答とログの回収、台帳ファイルの更新を行う。判断するモデルには数えない |
| 判断するモデル | Claude側とCodex側 | 各自が独立に結論を出す。モデルIDは実行ログで確認して台帳に書く |

環境ごとに誰がどの役割を担い、相手をどう呼ぶかは[references/claude-code.md](references/claude-code.md)と[references/codex.md](references/codex.md)にある。本文には環境ごとの呼び方を置かない。

## 手順

### 0. 問いを固定する

- 問いを1文に固定する。原資料とその版（コミットSHA、またはファイルパスと更新時刻）、制約、受け入れ基準を決める。
- 上限を決める（後述の「上限と停止」）。
- 入力に別のAIの結論が既にあれば、同じ問い・同じ資料の版を検討したものかを確認する。同じならその側の手順1を省き、その結論を再利用する。違う、または確認できなければ再利用せず、手順1を新しく実行する。

### 1. 独立に判断する

- 2つのモデルに同じ問い・原資料の版・制約・受け入れ基準を渡し、それぞれの結論を受け取る。相手の結論は見せない。呼び出し元の候補や推奨も見せない。
- 各モデルはこの手順でideationを使い、問題の枠と候補を自分で作ってから結論を出す。
- 相手CLIを呼び出す前に、呼び出し元は自分の初期判断を、許可された記録先のファイルへ保存する。記録するのは短い結論と根拠であり、内部の思考過程ではない。保存した本文を読み直し、ファイル情報から取得した保存時刻と、本文から計算したSHA-256を台帳に残す。
- 保存と確認が済むまで相手CLIを呼び出さない。許可された保存先がない場合や記録に失敗した場合は、未完了の理由を残して止める。記録がないのに独立判断を終えたと報告しない。
- この保存手順は呼び出し元に適用する。独立判断だけを依頼された相手の読み取り専用CLIには、ファイル保存や相手CLIの再呼び出しを求めない。
- 保存した初期判断は相手の応答を読んだ後も上書きせず、比較や推奨の変更は別に記録する。
- 相手の結論を見た後に書いた答えは独立判断として扱わない。台帳の備考に「相手の結論を閲覧後」と書く。

### 2. 主張台帳を作る

- 2つの応答を主張の単位に分け、[references/ledger-template.md](references/ledger-template.md)の形式で台帳を作る。
- 一致と不一致を分け、主張ごとに根拠（ファイルパス、コマンドの実測）を書く。根拠のない主張は状態を「未確認」にする。

### 3. 不一致を交換する（最大3ラウンド）

- 不一致の主張だけを選び、相手の原文を要約せずにそのまま根拠と一緒に渡す。
- 受け取った側は、新しい根拠があれば主張を修正する。なければ元の判断とその根拠を書き直して返す。
- ラウンドごとに台帳の判定・状態・ラウンドの列を更新する。
- 3ラウンドが終わるか上限に達したら、合意がなくても終える。

### 4. 報告する

後述の「報告の形式」で報告する。

## 上限と停止

- ラウンドは最大3回とする。
- ラウンドとは別に、呼び出しの総数と総所要時間の上限を手順0で決め、台帳の冒頭に書く。
- 根拠のない反論に対する呼び出しも呼び出し数に数える。
- 枠の組み直しや再検討（ideationの再実行を含む）も、同じ呼び出し数と時間の上限の中で行う。
- 合意せずに終わったら、不一致をそのまま報告する。終えるために合意を作らない。
- 呼び出しの失敗や時間切れは成功として記録しない。台帳の冒頭に理由を書いて終える。
- 相手の応答を回収できなければ、その側の独立判断は未取得とし、クロスチェックは未完了と記録する。別の実行担当による検証の合格で代えない。失敗の原因は`.err`と`.meta.json`で確認できた範囲に限り、ローカルファイルの権限エラーを、根拠なく認証・APIの問題に分類しない。
- 停止した条件を、再開の条件として使わない。上限に達して終えた検討を、同じ問いですぐに再実行しない。

## 再利用の条件

- 前の検討は、同じ問い・同じ資料の版のときだけ再利用する。資料の版はコミットSHA、またはファイルパスと更新時刻で確認する。
- 再利用する結論が相手の結論を見た後に書かれたものなら、その事実を備考に書く。

## 成果物

主張台帳が成果物である。台帳には、2つのモデルの実際の応答ファイルとモデルIDを記録する。交換した原文は要約せずに渡す。

## 報告の形式

1. 合意した点
2. 新しい根拠で修正された主張（何が、どの根拠で変わったか）
3. 判断として残った不一致と、それぞれの根拠
4. 未確認の点
5. 推奨1つとその理由

利用者の価値判断は、2つのモデルの合意で代えない。問いとして利用者に返す。

## スクリプト

`scripts/ask.sh`は相手のCLIを非対話で1回呼ぶ。

```bash
scripts/ask.sh <codex|claude> --prompt-file <F> --out-dir <D> [--cwd <dir>] [--timeout <秒、既定600>] [--model <id>] [--effort <low|medium|high|xhigh、既定high>]
```

- プロンプトはファイルのリダイレクトでstdinに渡し、EOFを保証する。
- `--cwd`は呼び出し元を基準に一度だけ絶対パスへ解決し、CLIとmetaに同じ作業フォルダを渡す。プロンプトと出力先の相対パスは、呼び出し元を基準にする。
- CLIは専用プロセスグループで実行する。時間切れでは同じグループにTERMを送り、2秒後にKILLを送る。親CLIの終了後も、同じグループに残る子を終了対象にする。
- `<D>/<side>-<時刻>-<pid>`を接頭辞として、次のファイルを残す。

  | ファイル | 中身 |
  |---|---|
  | `.out` | 応答本文 |
  | `.err` | stderr |
  | `.meta.json` | 依頼したモデル、実行ログで確認したモデルとその出典、effort、終了コード、開始・終了時刻、所要秒、時間切れの有無、状態 |
  | `.raw.json` | Claude側のCLIが出したJSONの原本 |

- `--model`を省くと各CLIの既定モデルを使い、実際に使われたモデルを`.meta.json`の`model_observed`に記録する。指定したモデルが拒否・代替された場合は`model_mismatch`をtrueにする。
- `--model`の値は観測したモデルIDと完全一致で比較する。別名や接尾辞は補完しない。Claudeの`modelUsage`に複数のIDがある場合は、指定したIDが含まれるかを確認する。
- effortは、Claudeには`claude -p --effort`、Codexには`-c model_reasoning_effort`で渡す。実際のeffortはCodexのrolloutとClaudeのセッション記録から読み、依頼と異なれば`effort_mismatch`をtrueにする。effortの不一致は終了コードを変えない。
- Codex側で書き込み後の点検を求めるフックなどが動くと、最後の応答が短い点検の返答になる場合がある。400字未満で、点検の定型句と句読点だけの応答を復元の対象にする。定型句の正規表現は環境変数`CROSS_CHECK_HOOK_REPLY`で変更できる。
- 復元にはrolloutの`response_item`にある`assistant`の最終応答だけを使う。`channel=final`、またはchannelが無い場合の`phase=final_answer`で識別する。両方の値が矛盾するメッセージは使わない。最後に記録された最終応答が`.out`と一致すれば、点検の返答を除いた直前の最終応答を長さに関係なく復元する。復元先は`.out`とし、元の応答を`.out.hook`に残す。復元できなければ元の`.out`を保持し、状態を`output_unverified`にする。途中の検討・進捗や、最終応答と識別できないメッセージは復元に使わない。
- 終了コードは、成功0、時間切れ124、使い方の誤り2、応答本文なし3、モデル未確認4、モデル不一致（拒否・代替）5、応答復元不可6、それ以外はCLIの終了コードである。時間切れ・モデル不一致・CLIの失敗・応答本文なし・モデル未確認は、応答復元不可より優先する。
- metaの確定は`scripts/collect_meta.py`が行う。
- `scripts/run_cli.py`はCLIの出力を指定ファイルへ書き、終了コード・時間切れ・起動エラーのJSONだけを`ask.sh`へ返す。helperの終了コードは、CLIの終了コード、シグナル終了なら128+シグナル番号、時間切れなら124とする。状態JSONの原文は`.meta.json`の`runner_result_raw`に保存し、別の状態ファイルは作成しない。
- 状態JSONが空・不正・helperの終了コードと不一致の場合は、成功にせず理由をmetaの`note`へ記録する。CLIが見つからなければ127、実行権限が無ければ126とし、`launch_error`を`note`へ記録する。CLI自身の終了コード124は、時間切れと区別して`error`にする。
- helperがSIGTERM・SIGINTを受けた場合は、専用グループへ直ちにKILLを送る。最初に受けたシグナルを`cancel_signal`として状態JSONに保持する。helperだけの取消では、SIGTERMは143、SIGINTは130とし、metaの状態を`error`、時間切れをfalseにする。
