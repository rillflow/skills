# 各モードの出力形式

会話の1行目にゲートの判定と手がかりを書く。出力ファイルを作る場合は、その1行目にも同じ内容を書く。資料の読み取り順はSKILL.md§1に従う。

すべてのモードで、事実と提案、担当・状態・期限の根拠、優先する理由の示し方はSKILL.md§6の共通規則に従う。

読み取り状況は、実際のツール呼び出しと結果で確認する。判定前に顧客受領情報を読んだ場合は、ゲート違反として読み取り済みと報告する。「読んでいない」と書かず、追加の資料読み取り・要約・台帳への転記を停止する。

```
ゲート: 社内情報のみ(実行環境: <名前>(手がかり: <確かめたもの>))
ゲート: 社内情報のみ(実行環境: 判定できない(<実際の確認結果または確認できない理由>))
ゲート: 顧客受領情報を含む(実行環境: <名前>(手がかり: <確かめたもの>), 許可: あり)
ゲート: 顧客受領情報を含む(実行環境: <名前>(手がかり: <確かめたもの>) または 判定できない(<実際の確認結果または確認できない理由>), 許可: なし — 顧客受領情報は読んでいない)
ゲート違反: 判定前に顧客受領情報を読み取り済み(実行環境: <名前と手がかり または 判定できない理由> — 追加の読み取り・要約・転記を停止)
```

policy.md が「書ける場所」を定める環境では、`prepare`・`digest`・`next`・`status`・`weekly` の出力をその場所のファイルに置き、会話には1行目の判定、変わった欄の要約、ファイルの場所を返す。
ファイル名は `<モード>-YYYY-MM-DD.md` にする。`prepare` は会議の日付を使い、同じ会議の準備なら既存のファイルを読み直して更新する。同じ日の別の会議なら `-2`、`-3` を付ける。ほかのモードは実行した日付を使い、同じ名前のファイルがあれば上書きせず、`-2`、`-3` を付ける。

## ask(日常の相談)

独立した相談は直接の答えを示し、必要なら次の行動を添える。台帳や出力ファイルは要求しない。案件の相談では、以下から判断に必要な項目だけを使う。

```
位置: <案件コード> <段階> — ここまで <一文> / この先 <一文>
(残っている仕事の相談なら、ここに未完了の約束と作業の表)
観点: <欄名または原則> — この相談では <一文>
      <欄名または原則> — <一文>
ビジネス: お金の流れ <値 or 未確認> / 顧客のアウトカム <値 or 未計測> / 原価 <値 or 未計測> / 次の案件 <値 or 未確認>
次の一手: 1. … 2. …
```

案件で「残っている仕事は何か」を相談し、台帳を使う場合は、「開いている約束」と「分岐した作業」の未完了を優先して示す。
相談が「作ったものの評価」なら、観点は B(単純な置き換えの兆候)と C(入口と出口、使う人)から選ぶことが多い。

複数の仕事から今日の行動を選ぶ相談は、SKILL.md§2に従う。以下のうち必要な項目だけを短く示し、全項目を埋めるために情報を集めない。提案した行動と、確定した約束を区別する。

```
今日優先すること: <行動>
目標・期待する結果とのつながり: <根拠 / 未確認>
今取り組む理由: <期限・詰まり・先行関係の根拠>
完了条件: <誰が次に何を判断・実行できるか>
確認すること・任せること: <必要なら>
今回は後にすること: <必要なら理由を添える>
```

## prepare

相手が顧客か社内の協業者かを確かめ、その相手が答えられる質問だけを選ぶ。顧客に確認する事実と社内で判断する原価・型の項目を分ける(SKILL.md§4)。

```
# 会議準備 <案件コード> <会議名> <日付>

## TCD の下書き
- Target / Constraints / Deadline(台帳から。無ければ「未設定 — 冒頭で確認」)

## 聞くこと(優先順)
1. <質問> — 観点: <欄名>(空欄 / 前回更新 YYYY-MM-DD)
   (5〜8個を目安とし、会議の判断に必要なものだけ)

## アジェンダ案

## 前回からの持ち越し
- 開いている約束
```

## digest

新しい記録で確認できた事実・決定・未決・約束を抽出する。次の行動の選択も求められたときは、その抽出結果を`next`へ渡す。同じ約束や要約を二度記録しない。

```
# 記録の整理 <案件コード> <記録名> <日付>

## 観点表の更新(変わった欄だけ)
| 欄 | 前の値 | 新しい値 | 根拠 |

## 決定 / 未決とその理由 / 約束(誰が・誰に・何を・いつまで・出どころ)

## 製品の不具合・要望(チケット下書き)
- 再現 / 期待 / 実際

## 次の作業(next へ渡す)

## 次の会議で聞くこと

## 週次ログ行
<日付> | <確認済みの案件コード / コード未定(下書き)> | <確認された変化のラベル> | <次の行動の種類のラベル>
```

約束と次の作業の期限・担当・出どころ・状態・状態の根拠は、[ledger.md](ledger.md)の規則に従う。

### 週次ログ行の組み立てと検査

詳細な要約を短くするのではなく、根拠のある抽出結果から、確認・更新した項目の名前だけを選ぶ。詳細は許可された台帳や本文に残し、週次ログ行には次のラベルだけを使う。

| 欄 | 許可するラベル |
|---|---|
| 確認された変化 | 目的確認、制約確認、担当確認、期限確認、約束確認、状態確認、確認事項更新 |
| 次の行動の種類 | 目的確認、制約確認、担当確認、期限確認、状態確認、進め方確認、次回確認、作業実施、結果確認、判断依頼、共有、記録更新、未定 |

ラベルが複数ある場合は` / `で区切る。変化のラベルは実際に確認・更新した項目に対応させる。次の行動の種類は、記録にある行動か、提案と明示した行動に対応させる。行動自体が決まっていない場合だけ「未定」とする。既知の行動がラベルに当てはまらなければ、未定にせず生成を保留する。ラベルは要約であり、実行の許可ではない。3・4欄には顧客名・個人名・業務名・文書名・原文の引用・URL・値を転記しない。

出力前に、各状態とその根拠の対応、ログの3・4欄の許可ラベルと抽出結果の対応を検査する。状態の根拠が無ければ[ledger.md](ledger.md)に従って「未確認 / 記載なし」とする。確認できた更新項目が無ければ行を埋めず、「ログ未生成: 確認できた更新項目なし」と示す。

ログに禁止内容や許可外の文言が残る場合、またはラベルを根拠に対応させられない場合は、行を出力・保存しない。「ログ生成保留」と理由だけを示し、詳細な業務内容を理由に再引用しない。下書きにも同じ検査を適用し、未生成・保留を成功や単なる省略として扱わない。

案件コードは[ledger.md](ledger.md)に従って確認したものだけを使う。コードが未定または顧客名に由来するときは「コード未定」とし、行をこの出力内の下書きにとどめる。コードを確認する必要と下書きの場所を利用者に伝える。追記には記録する権限が必要であり、確認済みコードの行だけをpolicy.mdに記した現在の環境の場所へ追記する。既存ファイルの部分更新はSKILL.md§8に従う。

## next

現在の状態から次の行動を選ぶ。`digest`の後なら抽出済みの事実を使い、記録の整理を繰り返さない。

```
# 次の作業 <案件コード> <日付>

## 分岐する作業
| 作業 | 種類 | 担当 | 期限 | 出どころ | 状態 | 状態の根拠 |

## 相手へ返すもの
- 誰に / 何を / いつまでに / 下書き

## 台帳の更新(新しく確定した内容があり、実際に更新した場合だけ)
- 更新した欄と出どころ
```

期限・担当・出どころ・状態・状態の根拠は、[ledger.md](ledger.md)の規則に従う。
種類がチケットのものは、下書き本文を末尾に付ける。起票するのは、利用者の指示があり、投稿先に接続できるときだけ(SKILL.md §6)。

## status

```
# 案件の現在地 <案件コード> <日付>

一言: <目的 → 段階 → 次の会議までにやること>

## 接点の時系列(直近5件)
## 開いている約束
## 観点表で空いている欄
## ビジネス A の現在値
```

## check

対象の本文だけで点検できる場合は、台帳なしで会話に答える。出力ファイルの作成や、原則・観点の全欄を埋めることは要求しない。

```
# 観点チェック <対象> <日付>

## 当たる原則(1〜3個)
- <原則> — この対象では <一文>

## 観点表で見ると
| 欄 | 対象での状態 | 見落とし・確認すること |

## 直すなら
1. …
```

## weekly

```
# 週次 <期間>

## 案件ごとの変化
| 案件コード | 段階 | 何が変わったか | 開いている約束 | 次週の焦点 |

## 観点表 A の変化
| 案件コード | 欄 | 前 | 後 |

## 空いたままの欄(3週以上)

## 次週の焦点(全体で3つまで)
```

前後の変化は、台帳や週次ログ行に比較できる過去の値と現在の値がある項目だけで示す。過去の値がなければ現在値と「過去の値は未確認」、測定値自体がなければ「未計測」とする。比較のために値を作らず、記録の原文を探し直さない。

`weekly`は、SKILL.md§1で許可された台帳と週次ログ行だけを材料にする。記録の原文を読み直さない。案件コードは[ledger.md](ledger.md)の規則に従う。

許可された台帳に実測値と比較できる過去の値があれば、観点表Aと前後の変化を示す。週次ログ行だけを読める案件は、確認された項目と次の行動の種類だけをまとめる。ログのラベルから詳細な業務内容・成果・数値を復元・推定せず、台帳の根拠を読めなければ未確認・未計測のまま扱う。

コードが未定または顧客名に由来する案件は、「コード未定」として案件ごとに行を分ける。複数あるときは、出力内だけの行番号で区別してコードの確認を求める。この行番号を案件コードとして保存したり、週次ログ行に使ったりしない。
