# 아이디어와 프레임 전환

지금의 문제 표현과 익숙한 해법에 묶이지 않고, 사용자가 쓸 수 있는 다른 관점과 실행 가능한 방향을 찾는다. 개인 발상과 상대에게 전달할 문안 모두 이 스킬만으로 완료할 수 있다.

## 깊이와 사용 상황

에이전트가 요청의 복잡성, 대화 상황, 판단의 중요도와 필요한 시간을 보고 깊이를 고른다. 매번 사용자에게 모드를 선택하게 하지 않는다. 짧은 아이디어 요청·대화·회의·회신은 보통 **빠른 모드**다. 여러 제약이 충돌하거나 같은 처치가 반복되고, 중요한 대안을 비교해야 하는 경우에는 명시적인 모드 요청이 없어도 **고찰 모드**로 진행한다.

사용자가 짧게·지금 바로·깊게·충분히 검토·풀 TRIZ처럼 깊이와 시간을 지정하면 그 지시가 우선이다. 대안을 비교한다는 말이나 글의 길이만으로 무조건 고찰 모드를 고르지는 않는다.

빠른/고찰은 탐색 깊이이고, 개인 탐색/공유·회신은 사용 상황이다. 빠른 개인 발상과 깊은 공유 준비도 가능하다. 사용자가 즉답을 필요로 하면 긴 조사를 먼저 시작하지 않는다.

## 기본 사고 원리

다음 중 현재 문제를 바꿔 볼 가치가 있는 관점을 고른다. 매번 모두 전개하거나 체크리스트로 출력하지 않는다.

- **목적과 수단**: 지금의 기능·문서·절차를 없애도 남아야 할 결과는 무엇인가. 해법을 이미 문제의 일부로 고정하지 않았는가.
- **상충의 전제**: 하나를 좋게 하면 다른 것이 나빠지는 이유가 실제로 확인됐는가. 두 요구가 같은 시간·장소·조건에서 필요한가.
- **해결할 위치**: 개인 작업, 구성요소, 전체 과정, 앞뒤 단계 중 어디에서 풀면 문제가 없어지는가.
- **기능과 자원**: 무엇을 더 넣기 전에 중복을 없애거나 역할을 옮길 수 있는가. 이미 가진 정보·기능·시간·결과물을 쓸 수 있는가.

관측 사실, 가정, 아이디어를 구별한다. 목적이나 상충을 억지로 만들지 않는다. 한 문제의 비용을 다른 사람·단계에 숨겨 넘긴 안은 그 비용을 함께 비교한다.

## 빠른 모드

이 본문만으로 짧게 한 번 검토하고 답한다. 심화 자료 정독, 다중 에이전트, 조사 보고서 작성은 기본 절차가 아니다. 해법의 성립을 좌우하는 사실만 필요한 범위에서 확인하며, 미확인 사실을 효과로 단정하지 않는다.

현재 표현을 바꿔 보는 관점과 곧바로 쓸 방향을 제시한다. 후보가 여러 개 필요하면 문구만 다른 답보다 작동 방식이 다른 소수의 안을 낸다. 사용자가 개수·분량·형식을 정했다면 그 요청에 맞춘다. 가벼운 발상에 빈칸을 채우기 위한 질문부터 나열하지 않는다.

내부 절차를 설명하는 대신 아이디어와 쓸모를 보여준다. 프레임을 바꾸는 것이 도움이 안 되면 정확한 답으로 끝내도 된다. 깊은 검토가 필요한 쟁점이 남으면 무엇을 더 확인해야 하는지 짧게 남긴다.

## 고찰 모드

[고찰 절차](references/deep.md)를 읽는다. 문제 재정의, 다른 해결 수준, 여러 작동 방식의 후보, 반례와 현실 제약을 검토한다. TRIZ 도구는 문제에 맞게 선택하며, 공학 모델이 성립하지 않는 문제를 모순행렬의 물성 항목에 억지로 넣지 않는다.

시간을 더 썼다는 사실이나 후보 수만으로 좋은 검토라고 판단하지 않는다. 어떤 가능성을 실제로 검토했는지, 무엇이 남았는지, 무엇을 시험하면 결론이 달라지는지를 남긴다. 모든 가능성을 전수 검토했다고 주장하지 않는다.

## 공유·회신 상황

개인 탐색에는 아래 전달 규칙을 강제하지 않는다. 사내 공유·회신을 요청받았을 때 적용하며, 고객 문서·PR 설명·툴 설명에는 그 산출물의 목적과 규칙을 따른다.

- **질문에 대한 회신**은 물어본 것에 먼저 정확히 답한다. 그 뒤의 더 큰 문제나 구조 개선이 도움이 되면 답을 덮지 않는 짧은 후속 단락으로 붙인다.
- **결과 공유**는 기능 목록보다 누가 무엇을 할 수 있게 됐는지, 이전 방식과 무엇이 달라졌는지, 적용 범위, 다음 행동을 보여준다. 이미 있는 실제 출력·수치가 설명에 도움이 되면 활용한다.
- 읽을 사람과 바꿀 판단·행동을 정한다. 결정할 사람이 다르면 적절한 담당자·채널을 제안한다. 반복 질문은 문서·기본값·기능을 바꿀 신호인지 검토한다.
- 이미 확인한 답을 공유하는 데 새 아이디어를 억지로 끼워 넣지 않는다. 없는 효과·숫자·고객 가치를 만들지 않고 가설을 확인된 사실처럼 전달하지 않는다.
- 행동 변화가 없는 공유는 기록으로 쓴다. 문안은 결론과 근거·범위·다음 행동을 중심으로 짧게 쓴다. 과장이나 작업 경위로 가치를 대신하지 않는다.

## 사용 경계

아이디어를 냈다고 설계 변경·코드 수정·게시 권한이 생기지 않는다. 사용자가 맡긴 범위에서 결과를 반환한다. 특정 구현·문서 리뷰 스킬을 필수 전후 단계로 호출하지 않는다.

원리의 근거와 효과의 확인 범위를 설명하거나 이 스킬을 갱신할 때는 [근거와 한계](references/evidence.md)를 읽는다. 일반 실행에서는 읽을 필요가 없다.
